# ADR 001: Rust for the data plane, Python for benchmarks

Status: accepted

## Context

Inferrail sits on the request path of every LLM call it routes. Its own
latency budget is under 1 ms at p99, scoring a request against 64 replicas
must stay under 200 µs, and streaming must add almost nothing per token. On
that path it tokenizes prompts, hashes thousands of token blocks, walks an
in memory index and proxies long lived SSE streams.

Everything around the router is different in kind: workload generators,
trace replay, statistics, plots and reports. That work changes often, leans
on numpy and pandas, and is never latency critical.

## Decision

* The data plane is Rust: every crate under `crates/`, including the
  simulator and the calibration tool. Async I/O uses tokio and hyper.
* Tokenization uses the Hugging Face `tokenizers` library, which is native
  Rust, so the hot path has no FFI hop and no GIL.
* Benchmark and analysis tooling is Python 3.12, managed by uv, under
  `bench/`. It talks to the gateway and engines only over HTTP and the
  committed result files, never through bindings.
* Golden fixtures that need the Python ecosystem (for example tokenizer
  parity with `transformers`) are generated by Python scripts and checked in,
  so Rust tests stay hermetic.

## Consequences

* Tail latency is predictable: no garbage collector, no interpreter, and
  allocation on the hot path is visible and testable.
* The boundary between the two languages is a wire protocol, so either side
  can be replaced or run on its own, and benchmarks measure exactly what a
  client would see.
* Two toolchains in CI. `make check` hides that behind one command.
* Contributors to the router need Rust; contributors to benchmarks do not.
